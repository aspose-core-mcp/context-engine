# ADCS Helm Chart

Production-oriented Helm chart for the ADCS runtime:

1. `api` deployment (public REST + admin API)
2. `mcp-gateway` deployment
3. `worker` deployment (ingestion)
4. `scheduler` deployment

Key baseline controls:

1. Readiness/liveness probes for all components
2. Resource requests/limits
3. HPA for `api` and `mcp-gateway`
4. PDB for `api` and `mcp-gateway`
5. Split ingresses for public/api/admin/mcp traffic
6. Default NetworkPolicy scaffold

## What you provide

The chart deploys the ADCS workloads only. Bring your own:

- **Container images.** Build them from this repository (`Dockerfile.api` and
  `Dockerfile.worker`, or the `api` and `worker` targets of `Dockerfile.k8s`), push them
  to a registry your cluster can reach, and set `api.image`, `mcpGateway.image`,
  `worker.image` and `scheduler.image`. Pull credentials go in `global.imagePullSecrets`.
- **Backing services.** PostgreSQL, a Redis-compatible store (such as Valkey), RabbitMQ,
  Qdrant and OpenSearch reachable from the cluster. Non-secret endpoints go in
  `global.externalServices`; credential-bearing connection strings go in
  `global.secretEnv`. The chart's NetworkPolicy allows egress only inside the namespace and
  to cluster DNS, so add a `networkPolicy.egressTo` entry (for example an `ipBlock` with the
  services' CIDR and ports) for services outside the namespace, or disable the policy.
- **An embedding endpoint.** The chart runs the `prod` profile, which rejects the
  deterministic development embedder. Point `global.env.ADCS_EMBEDDING_API_URL` at an
  OpenAI-compatible (or Ollama) embedding service running where your cluster can reach it.
- **Ingress hosts.** Replace the `*.adcs.local` placeholders in `api.ingress` and
  `mcpGateway.ingress`. MCP clients connect to `https://<mcp host>/mcp/v1/streamable-http`.

## Required values

The `prod` profile validates its configuration at start-up and refuses placeholders, so
pods fail fast with a clear message until these are set:

| Value | Purpose |
|-------|---------|
| `global.secretEnv.ADCS_API_KEY` | Admin API superuser key (`replace-me` is rejected) |
| `global.secretEnv.POSTGRES_DSN` | PostgreSQL connection string with real credentials |
| `global.secretEnv.RABBITMQ_URL` | RabbitMQ URL with real credentials |
| `global.secretEnv.ADCS_HASH_SECRET` | Key for hashing client IPs and query fingerprints |
| `global.env.ADCS_EMBEDDING_API_URL` | OpenAI-compatible embedding endpoint |

Optional:

- `global.secretEnv.ADCS_EMBEDDING_API_KEY` — API key for the embedding endpoint;
- `global.env.ADCS_EMBEDDING_MODEL` — embedding model name (the settings default applies
  when empty);
- `global.extraEnv` — any other setting from `.env.example`, for example
  `APIREF_STRUCTURED_STORE_ENABLED: "true"`.

Keep secrets out of values files and pass them at install time from your secret store:

```bash
helm upgrade --install adcs infra/helm/adcs \
  --namespace adcs --create-namespace \
  -f my-values.yaml \
  --set-string global.secretEnv.ADCS_API_KEY="$ADCS_API_KEY" \
  --set-string global.secretEnv.POSTGRES_DSN="$POSTGRES_DSN" \
  --set-string global.secretEnv.RABBITMQ_URL="$RABBITMQ_URL" \
  --set-string global.secretEnv.ADCS_HASH_SECRET="$ADCS_HASH_SECRET"
```

`my-values.yaml` holds the non-secret parts: image repositories and tags, service
endpoints, ingress hosts and the embedding endpoint. Escape commas in `--set-string`
values (`\,`), or supply such values through a values file generated by your secret store.

## Loading documentation

Ingestion reads the documentation sources — the git submodules listed in
`config/source-repositories.yaml` — from disk. The chart mounts no sources, so load the
corpus from a machine that has them: run `scripts/run_full_ingestion.py` with
`POSTGRES_DSN`, `QDRANT_URL`, `OPENSEARCH_URL` and the embedding settings pointing at the
services this release uses (see "Load documentation" in the repository README), then run
`kubectl rollout restart` on the `api` and `mcp-gateway` deployments: they cache query
responses in-process for up to 15 minutes.

## Local checks

```bash
make k8s-packaging-gates
```

This verifies chart structure and required production guardrails.

The MCP ingress also forwards `/words/net/mcp` unchanged to the gateway for the
Aspose.Words for .NET scoped endpoint at
`https://<mcp host>/words/net/mcp/v1/streamable-http`. If overriding
`mcpGateway.ingress.paths`, include this prefix. Do not rewrite it to `/mcp`: the
application selects the fixed product/language scope from the dedicated route.

The same API also serves Aspose.TeX for .NET at
`/tex/net/mcp/v1/streamable-http` (GET SSE and POST JSON-RPC). It fixes
`product_id="aspose.tex"` and `language="net"`, rejects conflicting scope,
and reuses existing TeX indexes with no additional ingestion. Its server name
is `aspose-tex-net-mcp`. Forward `/tex/net/mcp` through the ingress unchanged;
this prefix is included in the default Helm values. Installations overriding
`mcpGateway.ingress.paths` must include it explicitly.

The Total .NET endpoint is `/total/net/mcp/v1/streamable-http` (GET/POST).
Its allowlist is exactly `aspose.words` and `aspose.tex`, with language fixed
at `net`. Omit `product_id` to query both existing indexes; responses contain
`results_by_product`, each with `product_id` and `result`, or `not_found` for
missing symbols/releases. Limits and pagination apply per product, with no
cross-product score comparison. Explicit product selection returns the normal
single-product response. `resolve_product` without a selection lists the two
allowed products; free-text queries do not widen the scope. `aspose.total` is
not a stored product or an accepted product selection. Ingress must forward
`/total/net/mcp` unchanged (included in Helm defaults). No re-ingestion is needed.
